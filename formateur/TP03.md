# TP3 - Notes pour le formateur

## Minutage indicatif

| Partie | Durée |
|---|---|
| 1. Préparer le cluster | 15 min |
| 2. Gateway | 30 min |
| 3. Agent | 25 min |
| 4. Operator et auto-instrumentation | 30 min |

Si le groupe est en retard, la partie 4 reste la plus démonstrative : conservez-lui au moins 30 minutes et abrégez la lecture du rendu `helm template` de la partie 2.

## Exécution validée sur le groupe 0

Le TP a été joué de bout en bout sur `clt-0` (cluster KinD à trois workers) et `srv-0` (backend hors cluster). Ont été contrôlés : la création du cluster, l'installation de la Gateway API et de Traefik, les routes HTTPRoute, le déploiement de l'application et de Jaeger, la gateway et l'agent (chart Helm 0.179.1), la génération de traces avec `telemetrygen`, la redirection de la gateway vers le collector de `srv-0`, l'installation de l'Operator 0.129.1, l'auto-instrumentation des déploiements `frontend` et `backend`, et la collecte de logs avec le preset `logsCollection`.

Points relevés lors de l'exécution :

- Jaeger 2.23.0 ne répond que sur l'API v3 (`/api/v3/services`, `/api/v3/traces`) : l'ancienne API v1 renvoie 404, et la recherche de traces v3 exige une fenêtre temporelle explicite (`startTimeMin`, `startTimeMax`) ;
- le port publié par KinD n'est joignable que depuis le control-plane : Traefik doit y être toléré, sinon le DaemonSet ne s'y place pas et le navigateur reçoit une connexion refusée ;
- le nom de l'init container injecté est bien `opentelemetry-auto-instrumentation-nodejs` ;
- les noms de service obtenus dans Jaeger sont bien `frontend` et `backend` ;
- les attributs `k8s.*` sont présents sur les traces de l'agent, enrichis depuis l'adresse IP de la connexion ;
- le Deployment créé par le chart avec `fullnameOverride: otel-gateway` s'appelle `otel-gateway`, et non `otel-gateway-collector`.

## Points d'attention

- La Gateway API demande deux installations : les CRD `gateway.networking.k8s.io` (v1.7.0) puis une implémentation. Le chart Traefik ne fournit pas les CRD.
- Le Gateway créé par le chart n'accepte par défaut que les routes de son espace de noms (`namespacePolicy.from` valant `Same`) : sans `from: All`, les `HTTPRoute` de `demo` et `observability` sont ignorées et Traefik répond 404.
- Traefik tourne en DaemonSet avec `hostPort: 80` : toute mise à jour du chart peut bloquer, le nouveau pod du control-plane ne pouvant prendre le port tant que l'ancien le détient. Si cela arrive, supprimer les pods (`kubectl -n traefik delete pods --all`) et laisser le DaemonSet les recréer.
- Un seul cluster KinD par machine : le port 8080 publié est unique, et les instances `inotify` sont partagées. Avec les limites par défaut (128 instances), un second cluster ne démarre pas (« Too many open files » dans les logs du nœud) et peut déstabiliser le premier. Le cloud-init pose 512 instances et 524288 watches dans `/etc/sysctl.d/90-inotify.conf`, appliqués au démarrage et par `sysctl --system`.
- Le cluster s'appelle toujours `cluster`, quel que soit le TP, pour qu'un seul cluster existe par machine et que les TP Kubernetes se succèdent dessus : `config/tp03/cluster-create.sh` supprime celui qui porte ce nom avant de le recréer. Recréer efface releases Helm, espaces de noms et données, et un TP se rejoue depuis le début.
- Le terminal web ttyd écoute sur `127.0.0.1:7681`, derrière Caddy : le port 8080 de la machine reste libre pour le cluster.
- Ingress NGINX n'est plus maintenu que jusqu'en mars 2026 : c'est la raison de ce choix, et un bon sujet de discussion sur la pérennité des API.
- Les valeurs du chart sont validées pour la version 0.179.1, dont l'image par défaut est la 0.163.2. Ne pas changer `image.tag` sans reprendre cette validation.
- Le chart de l'Operator contient deux pods de test avec l'image `busybox:latest` (hook Helm `test`). Ils ne sont pas déployés à l'installation : ne pas lancer `helm test`.
- L'agent se planifie sur tous les nœuds qui acceptent ses pods : le control-plane garde sa taint, donc le DaemonSet de l'agent a trois pods, un par worker. Seul Traefik, toléré, tourne aussi sur le control-plane. Les applications de démonstration sont ainsi toujours colocalisées avec un agent, condition nécessaire avec `internalTrafficPolicy: Local` : un pod placé sur un nœud sans agent n'aurait aucune destination.
- Les types de composants ont été renommés : `otlp` est devenu `otlp_grpc` pour l'exporter et `k8sattributes` est devenu `k8s_attributes`. Les anciens noms restent des alias dépréciés, que les participants peuvent rencontrer dans d'anciennes configurations.
- Si une `Instrumentation` est créée après les pods, rien ne se passe : il faut redémarrer les pods (`kubectl -n demo rollout restart deployment/frontend`).
- Les ports 80 et 443 de la machine sont pris par le terminal web : les interfaces web passent par la Gateway API du cluster (Traefik), publiée sur `TCP/8080`.
- L'énoncé donne les fichiers de valeurs en entier : un participant bloqué peut les recopier, il n'y a plus de dossier `solution/`.

## Pour la discussion

- Gateway et agent répondent à deux besoins différents : la gateway centralise les traitements coûteux (échantillonnage, export vers plusieurs backends), l'agent reste proche des applications pour enrichir avec les métadonnées locales.
- Le chart ajoute ses propres valeurs : la fusion des dictionnaires et le remplacement des listes expliquent la plupart des surprises lors de la première installation.
- L'injection par l'Operator ne touche pas l'image de l'application : c'est ce qui la distingue d'une instrumentation par le SDK.
