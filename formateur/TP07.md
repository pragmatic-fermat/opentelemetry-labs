# TP7 - Notes pour le formateur

## Minutage indicatif

| Partie | Durée |
|---|---|
| 1. Démarrer sans instrumentation | 15 min |
| 2. SDK | 25 min |
| 3. Spans dans shop | 30 min |
| 4. Propagation | 30 min |
| 5. Logs | 20 min |

La partie 3 est celle où les participants hésitent le plus (choix des attributs, statut d'erreur). La partie 5 peut être donnée en démonstration en cas de retard.

## Ce qui a été testé

Le code des cinq modules, tel qu'il figure dans l'énoncé, a été exécuté en local hors Docker, avec les versions épinglées dans `config/tp07/app/requirements.txt` : deux processus Flask qui se parlent, avec des exporters remplacés par des exporters console pour contrôler les données produites. Sont vérifiés : l'état de départ (réponses 201, 409, 404 et aucun span), puis les modules instrumentés (une seule trace sur les deux services, reprise d'un `traceparent` entrant, statuts d'erreur, événements `stock.insufficient` et `exception`, logs reliés aux spans actifs). L'endpoint OTLP de Loki (`/otlp`) et les noms `trace_id` et `span_id` sont confirmés dans le code de Loki 3.7.10.

## Ce qui n'a pas été exécuté

À vérifier sur un pod :

- la construction de l'image (`docker compose up -d --build`) et le démarrage de la stack complète ;
- les commandes de vérification passées à l'API v3 de Jaeger 2.23.0 (`/api/v3/services`, `/api/v3/traces`, champs `status` et `events`) : elles remplacent les appels v1 de la première rédaction, retirés dans Jaeger 2.x ;
- l'appel `docker compose exec -T shop python -` avec un here-document dans le terminal web ;
- le lien Voir la trace des champs dérivés (`matcherType: label`) de Grafana 13.3.1 sur les métadonnées structurées de Loki ;
- la requête `trace_id != ""` de la partie 5 et l'API de proxy de Grafana (`/api/datasources/proxy/uid/loki/...`) ;
- la résolution d'un conteneur arrêté lors du test de panne : `requests` peut échouer sur la résolution du nom ou sur la connexion, dans les deux cas le service renvoie 502.

## Points d'attention

- Les modules `opentelemetry.sdk._logs` et `opentelemetry._logs` portent un préfixe `_` dans la version 1.45.2 : l'API des logs du SDK Python est encore présentée comme évolutive. Prévenez les participants que les noms peuvent changer dans une version ultérieure.
- Les dépendances de `requirements.txt` sont toutes épinglées, transitives comprises, et contiennent deux paquets en version `0.66b2` (`opentelemetry-exporter-http-transport` et `opentelemetry-exporter-otlp-common`) apportés par l'exporter OTLP/HTTP.
- Le serveur Flask utilisé est le serveur de développement : il est suffisant pour le TP, mais il affiche un avertissement au démarrage, qui est aussi le premier log (sans identifiant de trace) que les participants voient dans Loki.
- Si un participant appelle `telemetry.setup` plusieurs fois dans le même processus, le SDK affiche `Overriding of current TracerProvider is not allowed` et conserve le premier provider.
- Loki met une quinzaine de secondes à être prêt : si les participants testent la partie 5 immédiatement après le démarrage, les premiers logs peuvent être refusés.
- Les types de composants du collector ont été renommés : l'exporter `otlp` est devenu `otlp_grpc` et `otlphttp` est devenu `otlp_http`. La configuration fournie utilise les noms actuels, alors que la documentation de Loki utilise encore `otlphttp/logs` dans ses exemples.
- Le dossier `app/` étant monté en lecture seule, Python n'écrit pas de fichiers `.pyc` (variable `PYTHONDONTWRITEBYTECODE` dans le `Dockerfile`).
